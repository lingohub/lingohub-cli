# LingoHub CLI for the V2 API

The LingoHub CLI is a command-line interface tool that allows you to interact with the
LingoHub API. It is written in Rust and uses the `clap` crate for argument parsing and
`ratatui` to create a terminal user interface.

It uses a direct V2 HTTP client and a bundled backend OpenAPI contract. It must build
without a sibling SDK checkout. `lingohub-rust` is a separate SDK repository.

## Commands

Use Rust 1.98.1 (pinned in `rust-toolchain.toml`, as in CI and release builds) and Python 3.11+
for the scripts.

```bash
cargo fmt
cargo build --locked
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
python3 -m unittest discover -s scripts -p 'test_*.py'

LINGOHUB_API_KEY=lh-api_... cargo run -q -- your args here # Run the app with your arguments
```

## Requirements

The CLI should handle two main use cases:

1. Direct CLI usage: Users can pass arguments to specific operations to achieve some
   effect. This is done using key-value pairs on the command line directly. Optionally, a
   file can be provided to manipulate an HTTP request directly (e.g. passing a JSON
   body). This can also be used to capture `stdin`.
2. Interactive mode: Users can call the TUI to directly interface with data in an
   interactive dashboard-like fashion. This is done using the `tui` subcommand. The TUI
   should allow users to navigate through different sections of the LingoHub platform.

## Architecture

### File layout

```
src/
  main.rs              # Trusted user config before runtime startup, CLI dispatch
  api.rs               # Wire models and fetches for the TUI
  transport.rs         # Authenticated, bounded V2 JSON HTTP client
  contract.rs          # Once-per-process OpenAPI parse and operation lookup
  error.rs             # Central errors and RFC 9457 response handling
  prompt.rs            # User interaction via CLI prompts (e.g. Y/N questions)
  tui_app.rs           # TUI App state, event loop, BgMessage, draw_app
  action.rs            # Action enum and map_key — TUI intents and key bindings

  components/
    mod.rs
    api_key_input.rs   # API Key input screen
    workspace.rs       # Workspace dashboard panel
    tree.rs            # Stacks and projects dashboard

  cli/
    mod.rs
    parse.rs           # Clap arguments and shared resource actions
    input.rs           # Shared prompt helpers + read_body_source
    output.rs          # Wire JSON/human fields, headers and partial-outcome validation
    resource.rs        # Stack/project/style-guide CRUD and paged interactive selection
    upload.rs          # Bounded multipart preparation from contract schemas
    download.rs        # Metadata checks and unauthenticated atomic artifact download
    wait.rs            # Bounded polling of the supported asynchronous resources
    mcp_catalog.rs     # OpenAPI → MCP JSON Schema 2020-12 conversion
    mcp_server.rs      # Selected tool execution over MCP stdio
    upgrade.rs         # Release lookup, daily update notice and `lingohub upgrade`

tests/commands.rs      # Real CLI process + strict loopback HTTP/stdio regressions
contract/              # Backend OpenAPI snapshot and immutable provenance
scripts/               # Contract sync, release binary smoke test and script tests
.github/workflows/     # PR verification (opt-in all-platform builds); v-release.yml is generated by dist
dist-workspace.toml    # Release targets, installers and Homebrew tap
```

### Adding a new CLI subcommand

1. Create a new enum variant in `cli/parse.rs` for the subcommand.
2. Add a new match arm in `main.rs` to call the appropriate runner function.
3. Implement the runner function in `cli/` (e.g. `resource.rs`)
4. If the subcommand requires user input, add prompt helpers in `cli/input.rs` and call
   them from the runner.
5. Use `cli/output.rs` for responses and partial-result exit status. Preserve full wire JSON.
   Decide in `cli/upgrade.rs::calls_api` whether the command may show the update notice.
6. Add process coverage for the behavior. Test servers must fail on unexpected requests;
   negative cases must assert the intended error, not merely a nonzero exit.

Only the trusted user `.lingohub` file supplies dotenv configuration; never load a
working-directory/parent `.env`. Load environment configuration before runtime threads.
Keep authentication in `transport.rs`; artifact downloads and release lookups must not
forward it. Use `scripts/sync-contract.py` on a clean official backend checkout (maintainers
with backend access) to update the contract; copy the committed Git blob and preserve its exact
revision/checksum. Do not hand-edit it.

Releases are built by `.github/workflows/v-release.yml`, which dist generates from
`dist-workspace.toml`: change the configuration and run `dist generate`, never edit the
workflow by hand. Pushing a `v*` tag publishes a release to every user and updates the
Homebrew tap; it is an owner action. See [the release guide](docs/distribution.md).

### Component trait

Every TUI screen is a struct that implements `Component` (`src/components/mod.rs`):

```rust
pub trait Component {
    fn draw(&mut self, frame: &mut Frame, area: Rect);
    fn update(&mut self, action: &Action) -> Option<Action> { … }
}
```

- `draw` is required; `update` is optional (defaults to a no-op).
- Both take `&mut self` so components can maintain ephemeral render state
  (scroll offsets, cursor position, etc.).
- `update` may return a follow-up `Action` to trigger further state changes.

### Event → Action → Component flow

```
crossterm event
      │
      ▼
  map_key()          in action.rs: (&App, KeyCode) → Option<Action>
      │
      ▼
  match action        in tui_app.rs::tui_run() — mutates app fields or calls app methods
      │
      ├─ app.submit() / app.refresh()   → spawn_fetch → mpsc channel
      │
      └─ component.update(&action)      (for component-local reactions)

  app.poll()          drains the mpsc channel each tick → component.set_data / set_error
```

### AppState — screen routing

`AppState` in `tui_app.rs` is a **routing-only** enum; it carries no payload.
All screen-specific data lives inside the component:

```rust
pub enum AppState {
    ApiKeyInput,
    Workspace,
    Erred,
}
```

`tui_app.rs` contains `draw_app` which matches on `AppState` and calls the appropriate
component's `draw`. The workspace screen combines workspace details with the stacks/projects
tree. `Erred` renders the previous screen with an error overlay.

### Adding a new screen

1. Create `src/components/my_screen.rs` and implement `Component`.
2. Add `pub mod my_screen;` in `src/components/mod.rs`.
3. Add a variant to `AppState` in `tui_app.rs`.
4. Add any new `Action` variants needed in `action.rs`.
5. Add a field `my_screen: MyScreenComponent` to `App`.
6. Wire the variant in `tui_app.rs` (`AppState::MyScreen => app.my_screen.draw(...)`).
7. Map keys to actions in `action.rs::map_key`, then handle transitions in
   `tui_app.rs::tui_run` and `App` methods as needed.

## Code Guidelines

Structures and functions should be documented (but not overly so), and the code should be
organized in an idiomatic Rust style. Do not pull in additional dependencies unless
told so -- ask the user first.

Do not add two spaces after a period in documentation comments. Use a single space.

## Vim Modeline

Add this Vim modeline to every file using code folds.

```rust
// vim: foldmethod=marker foldmarker=<<<,>>>
```

Code folding should be done using section comments like this:
```rust
// ~~~~~~~~~~ App <<<

fn something() {
    ()
}
// >>>
```

ONLY use folds for large portions of code that benefit from being hidden.

## Commits

When writing commit messages, do not include the "feat:", "fix:", etc. prefixes. Instead,
write a concise summary of the change in the present tense. Only include a description if
necessary.
